## Проблема
Людям сложно управлять личными финансами при наличии счетов в разных валютах. Ручной пересчет расходов по текущему курсу отнимает время, а без конвертации в единую валюту невозможно получить точную картину общих трат и финансовой статистики.

## Технологический стек
- **Backend:** Java 21, Spring Boot
- **База данных:** PostgreSQL
- **Миграции:** Liquibase
- **Контейнеризация:** Docker, Docker Compose
- **Внешние API:** Telegram Bot API, API Центробанка РФ

## Сценарии пользователя
**1. Добавить трату**  
Пользователь вызывает соответствующую команду, после чего выбирает одну из доступных валют, вводит название, сумму и количество. Данные об операции сохраняются в базе данных.

**2. Просмотр статистики**  
Пользователь вызывает соответствующую команду, выбирает период, за который хочет посмотреть статистику (день/неделя/месяц/год).  
Бот отправляет сообщение с потраченной суммой по каждой валюте, в которой пользователь совершал операции, а также итоговую сумму в валюте пользователя (по умолчанию, в рублях). Причем пересчет на неё ведется на основе архивных записях о курсах валют (на момент каждой из покупок).  
После чего пользователю предлагается посмотреть статистику за другой период или в другой валюте.

**3. Просмотр последних операций**  
Пользователь вызывает соответствующую команду, после чего бот присылает 10 последних совершенных пользователем операций.

## Архитектура проекта
### Хараĸтер нагрузĸи на сервис
- Оценочное число пользователей: ~2 500 активных пользователей в сутки
- Период хранения данных: 5 лет (для финансового анализа, налоговой отчетности, отслеживания изменений расходов)
- Частота обновления курсов валют: ежедневно (синхронизация с ЦБ РФ)

### Соотношение R/W нагрузки
Чтение (Read): ~85%
- Получение статистики расходов (периоды: день/неделя/месяц/год)
- Просмотр последних покупок
- Запрос текущих курсов валют
- Экспорт данных в CSV

Запись (Write): ~15%
- Добавление новых покупок (основная операция записи)
- Регистрация новых пользователей
- Обновление курсов валют (1 раз в день)
- Изменение настроек пользователя (предпочитаемая валюта)

### Объёмы трафика
Входящий трафик (от пользователей к боту):
- Средний размер запроса: ~0.3 КБ
- Среднее число запросов на пользователя в сутки: 4
- Входящий трафик в сутки: ~3 МБ/сутки

Исходящий трафик (от бота к пользователям):
- Средний размер ответа: ~2.5 КБ
- Исходящий трафик в сутки: ~25 МБ/сутки

### Объёмы дисковой системы
Оценочный объём базы данных за 5 лет с учётом индексов составляет ~5.7 ГБ. Для обеспечения устойчивой работы рекомендуется выделить 8–10 ГБ дискового пространства.

## Масштабирование сервиса
При росте нагрузки до ~10 000 пользователей в сутки применимы следующие меры:
- Вертикальное масштабирование:
  - увеличение CPU приложения до 8 ядер
  - увеличение RAM приложения до 16 ГБ
  - увеличение RAM PostgreSQL до 12 ГБ
  - использование SSD/NVME дисков

- Горизонтальное масштабирование:
  - 2-3 инстанса Spring Boot приложения за балансировщиком
  - репликация PostgreSQL (мастер + 2 реплики для чтения)
  - Redis cluster для распределённого кэширования

- Оптимизация хранения:
  - партиционирование таблицы purchases по месяцам
  - архивация старых данных (>3 лет) в объектное хранилище

## Запуск приложения
1. В файле [.env](.env) заменить `tg_bot_token` на API токен Телеграм бота
2. Запустить контейнер, с помощью `docker-compose up --build`
